# Pinfold 2.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: use `superpowers:subagent-driven-development` to execute this plan. The orchestrator dispatches one subagent per workstream per wave; tasks inside a workstream run in order. Task headers use checkbox (`- [ ]`) syntax for tracking.

**Repo root:** the executing session's own worktree (all paths below are relative to it). **Feature branch:** the branch that worktree is on, cut from `feat/app-improvements-fixes-34c712` (which carries this plan and the backlog); "the feature branch" below always means that branch. **Baseline:** commit `1455674`, version 1.7, 331 app tests, 82 parser tests, SwiftLint 0 errors and 3 `file_length` warnings.

**Goal:** Implement every ticked item of `docs/improvement-backlog.md` (55 item ids), delivered as one pull request with the marketing version bumped to 2.0.

**Architecture of the plan:** Five waves. Wave 0 (serial) splits the oversized view files and adds a handful of behaviour-neutral seams so that later workstreams own disjoint files. Waves 1 to 3 run parallel workstreams (parser streams verified with `swift test`, app streams with targeted `scripts/test.sh` runs under a build lock). Wave 4 (serial) does docs, lint tidy, the version bump, release notes, the CI workflow and the PR. Every fix lands test-first.

**Tech stack (as read in the repo):** Swift 6 language mode (`SWIFT_VERSION: "6.0"`, package `swift-tools-version: 6.2`), SwiftUI with MV + `@Observable`, `MKMapView` via `UIViewRepresentable`, Swift Testing (`@Test` / `#expect`), XcodeGen (`project.yml`), ZIPFoundation. Local toolchain observed at planning time: Xcode 27.2, Swift 6.4.2, SwiftLint 0.65.0.

## 1. Binding conventions (from `CLAUDE.md`)

- Build and test only through `scripts/build.sh`, `scripts/test.sh` (filter: `-only-testing:PinfoldTests/<Suite>`) and `cd PinfoldCore && swift test`. Never raw `xcodebuild`.
- `swiftlint lint` stays at 0 errors. Annotate intentional violations inline; never loosen a rule globally. `swiftformat` owns comma and brace style (a PostToolUse hook in `.claude/settings.json` formats edited Swift files; if a subagent's edits bypass it, run `swiftformat --swiftversion 6.0 <file>` before committing).
- Keep view `body`s small and keep `Task.detached` closures inside `nonisolated` free functions (SIL `ClosureLifetimeFixup` pathology, see `App/Views/FavoritesView.swift`).
- Do not add explicit `Sendable` to internal all-value-type structs.
- Tests inject a temporary `StorageLocations(root:)` under `FileManager.temporaryDirectory` and a fresh `UserDefaults(suiteName:)`; suites sharing `@MainActor` state are `@Suite(.serialized) @MainActor`.
- `EntryMetadata` Codable is hand-written: a new property means CodingKeys, `init(from:)` (with `decodeIfPresent`), `encode(to:)` and the memberwise init.
- `Pinfold.xcodeproj` is generated and committed. After files are added or removed it is regenerated and committed; in this plan only the orchestrator does that (section 5).
- `CLAUDE.md` says "commit only when explicitly asked". Executing this plan is that request for commits on the feature branch. It does not cover merging, tagging or releasing.
- `AGENTS.md` is byte-identical to `CLAUDE.md` today; any edit to one is mirrored in the other.
- Commit signing and pushing follow the owner's personal instructions: when running unattended, commit with `git -c commit.gpgsign=false commit` (per-command flag only, never a config change), push over HTTPS through `gh`, and say in the PR body that the commits are unsigned. Subagents commit the same way and never push.
- Never merge the PR, never push to `main`, never tag or create a release.

## 5. Parallel-execution rules for the orchestrator

1. **Isolation.** Every code-writing subagent works in its own git worktree created from the wave's base commit on the feature branch, on a branch named `ws/w<N>-<stream>` (for example `ws/w1-core-b`). Wave 0 and wave 4 run in the main worktree, serially. Nobody touches the primary checkout or `main`. If worktree isolation is unavailable, run the app streams of a wave one at a time in the main worktree and keep only the PinfoldCore streams parallel.
2. **File ownership.** A subagent edits only the files its tasks list plus new files it creates. Section 3 is authoritative. Ownership violations are a reason to reject the stream's branch.
3. **Xcode project.** Subagents never commit `Pinfold.xcodeproj`. `scripts/build.sh` and `scripts/test.sh` both run `xcodegen generate`, so a subagent's worktree will show a modified `project.pbxproj` after any test run: stage explicit paths only (never `git add -A`) and run `git restore Pinfold.xcodeproj` before committing. The orchestrator regenerates and commits the project once per gate (`chore: regenerate Xcode project (wave N)`).
4. **Who builds and tests.**
   - PinfoldCore streams verify with `cd PinfoldCore && swift test` (optionally `--filter <Suite>`) in their own worktree, as often as they like. Each worktree has its own `.build`.
   - App streams run only targeted suites, `scripts/test.sh -only-testing:PinfoldTests/<Suite>`, and only while holding the build lock below. They never run the full app suite or `scripts/build.sh`.
   - The orchestrator alone runs the full `scripts/test.sh`, `scripts/build.sh` and the gate in section 7, on the feature branch, with no subagent holding the lock.
   - `swiftlint lint` is read-only and cheap; any agent may run it at any time.
5. **Build lock.** Concurrent `xcodebuild` runs contend for the one iPhone 17 / iOS 26.5 simulator and install the same bundle id, so they are serialised across all worktrees with an atomic `mkdir` lock in the shared git directory:
   ```bash
   LOCK="$(git rev-parse --git-common-dir)/pinfold-xcodebuild.lock"
   until mkdir "$LOCK" 2>/dev/null; do sleep 20; done
   trap 'rmdir "$LOCK"' EXIT
   scripts/test.sh -only-testing:PinfoldTests/<Suite>
   ```
   Run lock + test in one shell invocation with a long timeout. The orchestrator removes a stale lock (no `xcodebuild` process alive) before each gate.
6. **Concurrency cap (plan's call).** At most 3 PinfoldCore streams and 4 app streams at once. Waves define dependencies, not a requirement to start everything simultaneously; start the next queued stream when one finishes.
7. **Commits.** One commit per task in the stream's worktree, conventional style as in the repo history (`fix(core): ...`, `feat(app): ...`, `refactor(app): ...`, `test(app): ...`, `docs: ...`). Subagents never push.
8. **Integration.** At a wave boundary the orchestrator merges each stream branch into the feature branch with `git merge --no-ff ws/w<N>-<stream>`. With disjoint ownership there are no content conflicts; a conflict means an ownership violation and is resolved by returning the task to its stream, not by hand-merging.
9. **Compile coupling between package and app.** PinfoldCore changes must be source-compatible for the app (new init parameters get defaults). The one planned exception is the new `KMLGeometry.point` case (CB-4), which makes two app `switch` statements non-exhaustive; the orchestrator applies that fix at gate G1 (section 7).
10. **No wave starts before the previous gate is green.** A gate failure is fixed by a single fix subagent on the feature branch, serially.
11. **Reviews.** At each gate, run `superpowers:requesting-code-review` on the wave diff. Give the security-sensitive tasks an explicit second look: CA-2, CA-3 (parser guards), DL-1 to DL-3 (network), DT-4 (network-link download), ST-1 and SY-2 (deletions).
